# Plan de dev nocturne — nuit du 29 au 30 juillet 2026

> Plan d'orchestration des sessions de développement autonomes de la nuit,
> préparé et piloté par la session orchestratrice. Source de vérité du
> périmètre : [spec-profondeur-gameplay.md](spec-profondeur-gameplay.md).

## Organisation

Le cœur du jeu (Phases A puis B) se développe **en séquence** — les deux
phases touchent les mêmes fichiers (`sprint_state.gd`, `resolution_screen.gd`,
`balance.json`) et les paralléliser créerait des conflits. Une tâche de
contenu indépendante tourne en parallèle.

| Tâche | Branche | Base | Quand |
|---|---|---|---|
| 1. Phase A — Fondations économiques + pression | `claude/nuit-phase-a` | `claude/create-repo-7gxz2q` | immédiat |
| 2. Phase B — Économie du joueur | `claude/nuit-phase-b` | `claude/nuit-phase-a` | après la tâche 1 |
| 3. Contenu backlog (préparation Phase C) | `claude/nuit-backlog-contenu` | `claude/create-repo-7gxz2q` | immédiat (parallèle) |

## Critères communs à toutes les tâches

- Une **draft PR** par branche, description en français, jamais de merge.
- Godot 4.7 headless est installé (`~/.local/bin/godot`). Les smoke tests
  doivent passer : `godot --headless --path game res://tests/smoke_test_logic.tscn`.
- Les `data/*.json` restent la source de vérité ; tout nouveau réglage
  numérique va dans `balance.json`, pas en dur dans les scripts.
- Style : commits en français, cohérents avec l'historique du dépôt ;
  GDScript typé comme l'existant ; textes de jeu en français.
- En cas d'ambiguïté de la spec : choisir l'option la plus simple, la
  noter dans la description de la PR (section « Décisions prises »).

## Tâche 1 — Phase A : fondations économiques + pression (§13-A)

Périmètre exact (spec §3, §4.1-4.5, §5, §8, §10, §11, §12) :

- **Roster & rôles** : `SprintState.roster`, rosters de départ et cap par
  entreprise (`companies.json`), production de capacité par rôle,
  pénalités d'absence de rôle, rendements décroissants, suppression de
  `capacity_bonus`. Salaires prélevés à chaque Résolution (ligne « masse
  salariale »).
- **Licenciement** : indemnités 2 pièces, Moral −4, Cynisme +3 par
  licenciement supplémentaire dans le mandat (`fired_count`).
- **Traits cachés** : `data/hidden-traits.json` (pool + poids 50/30/20),
  tirage à l'apparition du candidat, révélation **fin de période d'essai
  uniquement** (embauche + 2 sprints, ligne de journal). Les effets des
  traits cachés révélés s'appliquent.
- **Pièces 🪙** : gains (allocation +2/sprint, réduite à +1 si revue de
  board ratée ; performance `floor(revenu/4)` ; quick wins ; événements
  Inbox via pseudo-ressource `pieces`) et dépenses (shop, indemnités).
- **Shop unifié** : l'écran Recrutement devient le Marché — 2 candidats
  (`data/candidates.json`, ~12 entrées) + 2 pratiques
  (`data/practices.json`, ~8 entrées, +2 Cynisme par achat, effets des
  pratiques de la table §5.2 — au minimum Entretiens structurés opérante,
  les pratiques de révélation d'infos roadmap posent leurs flags pour la
  Phase C). Tirage par sac stocké dans `SprintState` (pas de re-tirage).
- **Pression** : décroissance Valeur perçue −2/sprint ; revue de board au
  sprint 6 (objectifs par entreprise affichés dès le choix du poste,
  overlay de verdict, récompenses/sanctions §8.2) ; remap des fins §8.3
  (Valeur perçue ≤ 5 ⇒ revenu nul, le couperet direct saute).
- **UI** : barre de ressources (pièces, effectif 5/7, icônes pratiques),
  écran de choix d'entreprise (roster, cap, objectifs), Marché, panneau
  Entreprise (roster + licencier, pratiques, objectifs), Résolution
  (masse salariale, pièces, attributs révélés).
- **Équilibrage** : tout dans `balance.json` selon §12.
- **Recette** : réécrire les stratégies des smoke tests (`stress`,
  `greedy`, `careful`) pour piloter les nouveaux systèmes. **Critère
  obligatoire : `careful` doit perdre avant la fin du mandat.** Le smoke
  test doit échouer (exit non nul) si `careful` survit.

Hors périmètre : Énergie et actions personnelles (Phase B), backlog à
points/epics/infos cachées (Phase C), combos/reroll (Phase D).

## Tâche 2 — Phase B : l'économie du joueur (§13-B)

Se construit **sur la branche de la tâche 1**. Périmètre (spec §7, §8.3) :

- Jauge **Énergie** 0-100, départ 70, côté jeu uniquement (pas dans
  `resources.json`), affichée dans le groupe « Vous » de la barre de
  ressources avec le Capital politique.
- **Régénération** +12/sprint modulée par le Moral (×1 ≥ 60, ×0.5 30-60,
  ×0 < 30), réglages dans `balance.json`.
- **Actions personnelles** (§7.2) : 1:1 (révèle un trait caché, candidat
  ou employé), Faire le taf soi-même (+2 capacité ce sprint), Négocier
  une rallonge (−8 Capital politique → +4 Pièces), Souffler (renoncer aux
  actions du prochain sprint → +10 régén). L'action « Plonger dans une
  feature » attendra la Phase C (pas de roadmap profonde encore).
- **Burn-out remappé** : fin de mandat sur Énergie ≤ 0 (`endings.json` /
  seuils dans `balance.json`), l'ancien déclencheur Valeur perçue disparaît.
- Les événements Inbox acceptent `energie` dans `effects`.
- Résolution : ligne delta Énergie + option Souffler.
- Smoke tests : les stratégies utilisent les actions personnelles ;
  vérifier qu'une spirale Moral bas → régén nulle → burn-out est possible
  (la stratégie `stress` devrait pouvoir la déclencher).

## Tâche 3 — Contenu backlog (préparation Phase C, §6)

Tâche de **contenu pur**, sans toucher à `game/` ni aux autres fichiers
`data/` (aucun conflit possible avec les tâches 1-2) :

- Créer `data/backlog.json` : ~18 entrées « Transformation agile » —
  features `{id, name, icon, description, costPoints (1-5), roi (0-3),
  clientImpact (−2 à +6), risk (−3 à +8), quickWin (bool), eras[]}` et
  3-4 epics `{…, epic: true, costPoints (8-12), effets à la complétion}`.
  Ton d'écriture : satirique corporate, cohérent avec
  `roadmap-features.json` et `inbox-events.json` existants.
- Veiller à la distribution : quelques features pièges (réclamées mais
  `clientImpact` négatif), quelques quick wins, du risque de dette varié.
- Documenter le schéma dans `docs/data-schema.md` (section backlog).
- Valider le JSON (parse + cohérence des plages de valeurs) — un petit
  script de validation jetable suffit, pas besoin de Godot.
